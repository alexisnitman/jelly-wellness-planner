# Harness: what the app stores or sends, and how it is protected

Last updated: October 16, 2026 (accounts, profile, calendar import and free time, week picker, week description and follow-up questions, plan proposal, real fitness classes, approval and .ics export).

## What is stored (`backend/data/app.db`, SQLite)
Git-ignored. Folder mode 0700, files mode 0600. Every query for user data is scoped to the logged-in user's id, which comes from the session cookie and never from the request.

| Table | Stored | Protection |
|-------|--------|------------|
| `users` | first name, email (lower-cased), username (lower-cased), `password_hash` | Password is an **argon2id** hash with a random salt; the password is never stored or logged. Email and name are plain text. |
| `sessions` | SHA-256 of the session token, user id, expiry | The raw token exists only in the browser cookie. A copy of the database can't be used to log in. |
| `profiles` | waking hours, week start day, time zone, city, diet and allergy notes, injury notes, **role** (student, working professional or other) and **role answers** (JSON: choices from that role's follow-up questions, such as course load or meeting load, or a short free-text description for "other") | Only reachable through the owner's session. Never logged. Role answers are validated against the allowed choices on the server, and answers that don't belong to the current role are dropped when the role changes. |
| `calendar_links` | the private calendar link **encrypted** (Fernet: AES with an integrity check), plus its host name only | Stored only if the user ticks "Remember this link". Never sent back to the browser, never logged, never sent to a model. The user can forget it at any time. |
| `password_resets` | a SHA-256 hash of each one-time reset token, the user id and an expiry 30 minutes ahead | The token itself is never stored. A row is deleted when used or replaced by a newer request, and with the account. |
| `search_cache` | per user and week: the verified classes, restaurants or movies found for the user's request (names, times, page links, the request signature) | Public web information only, no profile data or calendar contents. Scoped by user id, deleted with the account, rows older than a day are deleted. Kept in the database so a server restart doesn't break approving and exporting a plan. |
| `ai_usage` | day, feature name, tokens, web searches, estimated cost | No user content: no calendar data, plans, prompts or answers (checked by a test). |

Encryption key: the `APP_ENCRYPTION_KEY` environment variable if set, otherwise a key file `backend/data/app.key` created on first use (mode 0600). A key file next to the database protects against a leaked database or backup, but not against someone who can read the whole data folder. For stronger protection set `APP_ENCRYPTION_KEY` from a `.env` kept elsewhere.

**Never stored anywhere:** uploaded .ics files, calendar events (titles, attendees, locations, descriptions), busy or free results, plans. Nothing about accounts, profiles or calendars is kept in the browser's localStorage.

## Passwords and sessions
- Passwords: argon2id (argon2-cffi defaults), 10 to 128 characters, rehashed at login if the parameters are upgraded.
- Login errors always say "Invalid username or password" (a dummy hash is verified for unknown usernames so timing doesn't reveal them). Five failed logins within 15 minutes lock that username and that client address for 15 minutes (in memory; resets on restart). Registration reveals only that "username or email is already in use".
- Sessions: random 256-bit token in an `httpOnly`, `SameSite=Lax` cookie (`Secure` when `COOKIE_SECURE=true`), 30 days from last use (sliding) or until logout. Logout deletes the session row.
- **Forgotten password (local mode):** `POST /api/auth/forgot` takes an email and always gives the same answer whether or not it has an account (so emails can't be probed); if it does, a one-time token is made (256 bits, hash stored, 30 minutes, an older unused link is replaced) and the link `http://localhost:5200/?reset=<token>` is **printed in the terminal window running the backend** (`reset_delivery.py`; no email is sent, so whoever runs the app passes the link on; it also lands in `backend/server.log` if the server's output is saved there, but it works only once and expires). `POST /api/auth/reset` sets a new password (10 to 128 characters) from a valid link, signs the account out everywhere, clears any login lockout and consumes the link. Requests are throttled (5 per email and per address per 15 minutes; 5 bad link attempts per address). The page keeps the token in memory only and removes it from the address bar at once. To send real email later, replace `deliver` in `reset_delivery.py`.

## Calendar privacy
- The calendar is **read-only**: the app never writes to or changes it. Output (later) is an .ics file the user imports themselves.
- `lib/calendar/parse.py` turns a calendar into **busy time ranges only** (start and end). Titles, attendees, locations and descriptions are never copied into any result, response or log (tests check this). Events marked "free" and cancelled events don't count as busy; repeating events, time zones and all-day events are handled.
- Free time = waking hours minus busy time, computed by code (`lib/calendar/free_time.py`), not by a model.

## Private calendar links
A private link is a secret (anyone with it can read the calendar). Fetching is restricted (`lib/calendar/fetch.py`): https only (`webcal://` is converted), no embedded passwords, **public addresses only** (localhost, private networks and link-local addresses such as cloud metadata are refused), every redirect re-checked (max 3), 10 second timeout, 5 MB cap. Error messages never include the link. The link is sent in a request body (not the URL) so it doesn't appear in server access logs. The password-style input in the page hides it on screen, and the page forgets it after it is sent.

## What is sent to a model
Three steps call a model (all `gpt-6-luna` through `lib/llm`, login required, tagged by feature name only).

**Step 2, the interview** (`POST /api/interview/questions`, `agents/interview_agent.py`) receives:
- the week description: sentences built from the user's form choices (including an optional "About me" line: whether they are a student or working professional, how busy the week is, and up to three priorities) on the first page (how many workouts and of what type, meals and cuisines, other categories) plus anything they typed in the two optional boxes (up to 2,000 characters in total, labelled as data so instructions inside it are ignored), and
- the user's waking hours, plus **yes/no flags** saying whether a city, diet and allergy notes and injury notes exist in the profile (so it doesn't re-ask), plus **who they are** from the profile as one line made only of the allowed choices (for example "a student: undergraduate; mornings; heavy; on campus" or "a working professional: hybrid; back-to-back; 30 to 60 minutes", or the short free text for "other"), so it asks role-specific questions and never re-asks. The profile text itself, the name, email and username are never sent. The profile is read on the server from the session, never from the request.

It does **not** receive the calendar, busy or free times, event details, or the private link. Later phases will send only busy and free time ranges, the user's answers and week description, and (when needed) the profile notes the planner must respect; each change will be listed here. The request is tagged with the feature name only (`interview`). The model's output is validated in code (3 to 5 questions, unique ids, bounded text, choice questions need choices) before the page renders it. The question page is login-only so anonymous visitors can't spend the model budget.

**Step 4, the planner** (`POST /api/plan/propose`, `agents/planner_agent.py`) receives, by the user's choice that profile notes are sent to the model so plans respect them:
- the week description (as above), the goals (exact counts and types built in the browser from the user's form choices, plus any extra goals the question step found in their free text) and the user's answers to the follow-up questions (the user's own words, labelled as data);
- the **profile notes**: who the user is (the same one-line role summary), city or neighborhood, diet and allergies, injuries or limits. These are health-related, so they leave the server only for this call and are read from the user's account on the server, never from the request;
- the waking hours and the **free time windows** for the chosen week (or just the waking hours if the user skips the calendar).
**Revisions:** when the user asks for a different plan, the planner also receives their change request (up to 600 characters of their own words, labelled as data, so it can't change the rules or override the diet and injury notes), the plan they were looking at (item titles, types, days and times: the model's own earlier output) and the titles of items they removed. A revision runs the same validation as a first plan.
It does **not** receive busy time, event details, the private link, or the user's name, email or username. The free windows come from the browser, but the server re-clips them to the week and the user's waking hours. Requests are tagged `planner` or `planner_repair`.

**Movie nights** (`agents/movie_agent.py`, run only when the user picks "Movie night" under Friends & family and answers how many, **theater or stay in**, and genres (up to 3); "Game night" is now its own plain option; tagged `movie_finder`) receives only: the city (theater only), theater or home, the genres and the week's dates. It does **not** receive the calendar, free time, profile notes, name, email or username. Same tools and limits as the other finders (web search, `fetch_page`, at most 5 pages, page text untrusted). It returns a **short list (up to 5)** shown on the plan page with a link for each. **Code decides what is real** (`verify_movies`): a movie is kept only if its page was downloaded in this run **and its title appears in that page's text**; a showtime only if it appears in the text, is in the week, not past, and a 150 minute outing fits free time; a theater or streaming service name only if the page mentions it; links must be http(s). Theater lists come from pages like Showtimes or a cinema's site, home lists from pages like Rotten Tomatoes (genre inferred only from a genre-filtered list the agent read); showtimes are usually drawn by scripts, so most results are "playing near you, showtimes not confirmed". The planner may use a movie only by id (validator: exact showtime if one was read; otherwise a start between 12:00 and 21:30, 2 to 3.5 hours at a theater or 1 to 4 hours at home). The app buys no tickets and never says seats or a stream are available beyond what a page showed. Cached 6 hours per user and week in `search_cache` like the other finders; export takes movie details from the cache.

**Workout detail:** the planner is told to write each workout like a coach's session: every exercise on one line with sets and reps (or a time, distance or pace), rest and a short form cue or easier option (for example "Pull-ups: 3 sets of 8 reps, rest 90 seconds. Start from a full hang; use a band or inverted rows if you can't yet"), 4 to 7 exercises for strength, counts or times on every warm-up and cool-down line, and only equipment the user has. Code enforces it: a workout (other than a real class) needs at least 3 `main` lines and at least 80% of them must contain a number, otherwise it is rejected with a reason and goes through the one repair pass. The calendar event lists the warm-up, exercises and cool-down.

**Follow-up questions for bundled options (step 1):** options that bundle alternatives (for example Coffee or drinks, Yoga or Pilates, Outdoor activity, Game night, Event or show, Appointments, Cleaning or chores, Breathing or meditation) open a "pick any" follow-up asking which one(s). The answers are plain text added to the week description and goal notes the planner reads (for example "Coffee or drinks (Tea)"); the choices are fixed lists in `frontend/src/lib/week.ts` (`REFINE`). The old "Meal out" option was merged into "Go out to eat".

**Ingredients and grocery trips:** when the user picks Cooking they can list up to 8 ingredients to use (short text, cleaned, no links) and ask for a grocery shopping trip. The ingredients go to the planner (they are also in the week description) with the instruction to build them into recipes, with diet and allergy notes still first. After planning, code checks which ingredients appear in some recipe and lists any that don't as "Ingredient not used". A grocery trip is an ordinary errand goal that the planner is told to schedule before the first cooked meal (validated like any other item).

**Real fitness classes** (`agents/class_agent.py`, run only when the user picks "A fitness class" and says which studio or "something new"; tagged `class_finder`) receives only: the city (from the profile, or typed for this search), the studio name the user typed or "something new", the class types they picked, and the week's dates. It does **not** receive the calendar, free time, profile notes, name, email or username. It uses the model's built-in web search plus a `fetch_page` tool (`lib/web/fetch.py`: public http(s) pages only, private and loopback addresses refused, redirects re-checked, 8 second timeout, 400 KB cap, text pages only, at most 5 pages, results wrapped as untrusted data). The page text is untrusted: the prompt says to ignore instructions in it.
**Code decides which classes are real** (`verify_classes`): a class is kept only if (1) its source page was actually downloaded in this run, (2) its start time appears in the text of that page (formats like 6pm, 6:00 PM, 18:00), (3) the times and length are valid (20 to 150 minutes), (4) it falls in the planned week (weekly timetable entries are expanded to dates) and not in the past, and (5) it fits entirely inside one of the user's free windows. If the page lists only start times the class is kept but marked "length assumed". The planner may schedule a class only by its id with its exact day and time (the validator rejects invented classes, changed times and reuse), and the plan shows the studio, address if listed, a link to the schedule page that was read and the date it was read, with "times can change, confirm and book on their site". Studios whose schedules are drawn by scripts can't be read; they are listed with a link so the user can check themselves, and the plan says how many requested classes could not be scheduled. Nothing is booked for the user.
Verified classes are cached in the database (`search_cache`) for 6 hours per user and week (public schedule data, no profile data), so a revised plan doesn't search again; export takes class details from that cache and refuses a class that isn't in it or whose time was changed ("your class details have expired, propose the plan again").

**Meals out** (`agents/restaurant_agent.py`, run only when the user picks "Go out to eat" under Friends & family and answers how many, **which meal (breakfast, brunch, lunch or dinner)**, **reservation or walk-in**, for how many people and the cuisines or a restaurant they have in mind; tagged `restaurant_finder`) receives only: the city, the party size, the cuisines or restaurant name the user typed, and the week's dates. It does **not** receive the calendar, free time, **diet or allergy notes**, name, email or username (the planner, which does see the notes, tells the user to confirm allergies with the restaurant). It returns a **short list (up to 5)** shown on the plan page with each restaurant's booking link. *Reservation* lists keep only restaurants with a booking link the agent saw (or whose own page says they take reservations); *walk-in* lists keep restaurants with no booking link found, ranked first when the page itself says walk-in (the exact words must appear in the page text), otherwise labelled "no booking site found". Links are never built by the model or the app. Same tools and limits as the class finder (web search, `fetch_page`, at most 5 pages, page text untrusted).
**Code decides what is real** (`verify_restaurants`): a restaurant is kept only if its source page was downloaded in this run; a reservation time is kept only if it appears in that page's text, is in the week and not past, starts in that meal's hours (breakfast 07:00 to 10:30, brunch 09:30 to 13:30, lunch 11:00 to 14:30, dinner 16:30 to 21:30) and a meal of that length (60, 90, 75 or 90 minutes) fits a free window. Most booking sites (OpenTable, Resy, Tock) draw their times with scripts, so usually **no time can be read**: the restaurant is then shown as "table not booked, availability not confirmed" with a link to check and book, and the planner picks an evening free window for it (validator: a start in that meal's hours and a sensible length for it). The planner may use a restaurant only by id; a listed time must be used exactly. **Jelly Wellness Planner never books, holds or checks out a table and never says a table is free unless a time was read from a page** (and even then the page says it may be gone). The calendar event says "A table is NOT booked", gives the page that was read and the booking link, and tells the user to mention allergies. Restaurants are cached 6 hours in `search_cache` (per request style, city, party size and cuisines) per user and week; export takes restaurant details from that cache and refuses an unknown restaurant or a changed time.

**Evidence for "why this helps"** (`lib/evidence`, `lib/evidence/claims.json`): the planner also receives the user's priorities (up to three of: more energy, less stress, better sleep, consistency, fitness, time with people, focus) and a fixed list of evidence ids with exact quotes. Nothing is searched at run time. The list holds 35 quotes copied word for word from medlineplus.gov, nhs.uk, nhlbi.nih.gov, nimh.nih.gov, nccih.nih.gov, hsph.harvard.edu (The Nutrition Source) and similar official pages, each with its link and the date it was checked (`scripts/verify_evidence.py` re-downloads every page and fails if a quote is no longer there; it retries because some sites sometimes serve a shorter page). The model picks ids and writes one plain sentence per item; code then (1) drops unknown ids, (2) keeps a claim only if it applies to the item (right activity type, matching words in the title or workout, ingredients really in the recipe, a dinner that ends at 8 PM or later for the late-meal tip), (3) shows at most three claims, ones serving the user's priorities first, with the quote, source name, link and date taken from the list (never from the model), (4) names a priority in the lead line only if a shown claim's quote itself states it ("Linked to your goal of…"), or labels an inference "Related to your goal of…", and (5) shows the model's sentence only if it has no numbers, links or words like cure, treat, prevent, heal or proven. If no claim applies, no benefit text is shown. This text appears in the app only: as of Oct 19, 2026 the calendar file does not carry "why this helps" (no quote, source or link), so nothing from the evidence list leaves the app.

**What the code does with the model's plan** (`lib/plan/validate.py`, `lib/plan/diet.py`): nothing is trusted. An item is kept only if it fits entirely inside one free window and the waking hours, is in the chosen week, has a sensible length (10 minutes or more for wellness habits, 15 for everything else), has at least 15 minutes between it and its neighbours, doesn't overlap another item, stays within 4 items a day, adds up to no more than 5 hours of planned activity that day (rest and wellness breaks don't count), for workouts ends at least an hour before the waking hours end so exercise doesn't cut into sleep, and (for recipes) has no ingredient that matches the diet or allergy notes. Failed items get one repair attempt with the reasons; anything still failing is listed under "Couldn't fit", never in the plan. The diet check is conservative: any allergen or diet word in the notes (peanut, nuts, dairy, egg, wheat or gluten, soy, fish, shellfish, sesame, vegetarian, vegan, pescatarian, no pork, no beef) is treated as something to avoid, matched on whole words, so it can reject too much but shouldn't miss an obvious conflict. Links the model writes are stripped, the word "safe" is replaced, and the model is told not to name any specific venue, business or price (local suggestions come in a later phase). Every plan shows a "not medical advice" note. The workout and recipe details are general ideas, and the injury note is only a prompt for the model: the code cannot verify a workout is appropriate for an injury.

**Approval and export** (`POST /api/plan/export`, `lib/plan/ics.py`) make **no model call**. The user ticks which items to approve; only those items are sent. The server re-validates them against the same rules as the proposal (free windows, waking hours, week, buffers, overlaps, per-day limit, diet and allergy notes) and refuses the whole export with the reasons if anything fails, so nothing the checker wouldn't allow can end up in a file. It also refuses anything in the past: free time before "now" is never offered to the planner and past times are rejected on export. Text is cleaned (control characters and line breaks removed, links stripped, the word "safe" replaced) and escaped by the icalendar library, so a title can't inject extra calendar lines (tested). The file is a plain calendar file (no invitations, no alarms) with proper time zone definitions and one event per approved item, with the recipe or workout in the event notes and a "not medical advice" line. The file is generated on request, handed to the browser as a download and **not stored on the server**. The app never writes to the user's calendar; the user imports the file themselves (steps are shown after download).

The **week calendar picture** on the approval step is drawn in the browser from data already in page memory (the busy time ranges the calendar read returned, never event titles or details, and the proposed plan). Nothing extra is sent anywhere to draw it.

Answers, the description, the calendar result and the plan live in **page memory only** (not localStorage, not the server) and are lost on reload or logout.

## How the backend and front end talk
React calls relative URLs (`/api/...`); the Vite dev server (port 5200) proxies them to FastAPI (port 8000), so the browser sees one origin and the cookie is first-party. State-changing requests from other origins are refused; validation errors never echo submitted values; every response has `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`.

| Endpoint | Auth | Purpose |
|----------|------|---------|
| `GET /api/health` | none | Server up, model name, AI on/off, spend today |
| `POST /api/auth/register`, `/login`, `/logout`, `GET /api/auth/me` | none / cookie | Accounts |
| `POST /api/auth/forgot`, `/reset` | none | Forgotten password: create a one-time reset link (printed in the backend terminal); set a new password with it |
| `GET`, `PUT /api/profile` | cookie | The user's own profile |
| `POST /api/calendar/read` | cookie | Read a file, a link or the saved link for 1 to 8 consecutive weeks (the page reads 6 so the week picker can move around); returns busy and free ranges |
| `POST /api/interview/questions` | cookie | Step 1 to 2: turns the week description into goals and 3 to 5 follow-up questions (model call) |
| `POST /api/plan/export` | cookie | Steps 5 to 6: builds the .ics from the approved items after re-validating them (no model call); returns the file as a download |
| `POST /api/plan/propose` | cookie | Step 4: proposes a plan for one week from the description, answers, profile notes and free windows; validated in code (model call, up to 2 per request) |
| `POST /api/plan/prefetch` | cookie | Starts the slow web searches (classes, meal out, movie) in the background for the same request and week the plan step will use; returns at once, shows nothing, schedules nothing (model calls, same limits) |
| `GET`, `DELETE /api/calendar/link` | cookie | Whether a link is saved (host only) / forget it |

## Model gateway (`backend/lib/llm`)
**Speed.** Measured on Oct 17, 2026: the question step takes about 4.5 seconds and the plan itself about 16 seconds when no searches are needed; the web searches (class, meal, movie) are the slow part, and a stalled connection used to wait up to 10 minutes. Now: every model call has a timeout and one retry (`FEATURE_SETTINGS`: 30 s for questions, 150 s for the plan, 90 s for each search) and fails with "The AI took too long to answer, please try again"; the finders are told to read their pages in one step; the searches don't need the calendar, so when the user finishes step 1 the page calls `/api/plan/prefetch` and they run while the user answers questions and adds the calendar (the plan step then only does the code check against free time, with the same page-verification rules; a failed or mismatched early search falls back to a normal one). Reasoning "none" is used for the question step (it made no measurable difference to the speed of the others, so they stay on "low").
When a request asks for classes, a meal out and/or a movie, those three searches run **at the same time** (they are independent), then the planner runs once. Each model call logs only its feature name, duration and token counts (never prompts or answers) so slow steps can be found.
`gpt-6-luna` only, through Portkey (`PORTKEY_API_KEY` from a `.env`, server side only), tagged with the feature name only. Limits in `LIMITS`: 16,000 characters of input, 4,000 output tokens per response, 12 steps, 250,000 input and 20,000 output tokens per run, $1.00 daily cap, `AI_ENABLED=false` kill switch. A limit pauses AI with a clear message and never falls back to another model. Cost estimates use third-party price figures ($0.10 / $0.01 cached / $0.50 per million tokens, $0.01 per web search): verify against OpenAI's pricing page.

## Tests
`cd backend && ../.venv/bin/python -m unittest discover -s tests -v` runs 232 checks with no network or model calls: the gateway rules; busy-time maths (time zones, DST, repeating, all-day, free-marked, cancelled, merging); free-time windows; that no event detail ever appears in results; link rules and refusal of private addresses (and that errors don't echo the link); encryption round trip, opaque ciphertext and key file mode; profile validation; per-user isolation of profiles and saved links; unauthenticated and forged cookies refused; passwords and tokens not stored in plain text; uniform login errors; the interview agent's output validation (3 to 5 questions, choice questions need choices, unique slug ids, bounded text, goals bounded); that only yes/no profile flags reach the model; login required for the interview route; a clear 503 when AI is paused; description limits; multi-week calendar reads; the plan validator (free windows, waking hours, week, lengths, buffers, overlaps, per-day cap, recipe conflicts with allergy and diet notes, whole-word matching); the planner's repair loop (unfixed items become "couldn't fit", failed repair keeps the first result, nothing silently dropped); that the prompt carries notes and free time but no busy or calendar details; link stripping and "safe" scrubbing; and the revision prompt (change request, current plan and removed items reach the model only on a revision, and the rules say a change request can't override diet or injury notes) and the cleaning and limits on those fields; the plan route (profile from the session, no-calendar mode, clipping to waking hours, week start check, 503 when AI is paused, the past never offered); and dinner reservations (restaurant and slot verification, validator rules, prompt contents, what the finder is and isn't sent, cache and export); and the export (a valid calendar with one event per approved item, unique ids, time zone definitions, wall-clock times across a DST change, recipe and workout details in the notes, injection of calendar lines and links blocked, "safe" never written, only the approved items exported, re-validation against free time, overlaps, waking hours, diet conflicts and the past, request limits).

## Known gaps
1. The database is not encrypted at rest (only the calendar link is). Names, emails, profile notes and diet or allergy notes are readable by anyone who can read the file.
2. No HTTPS locally: set `COOKIE_SECURE=true` and serve over HTTPS only before any deployment.
3. No email verification or account deletion yet. Password reset works in local mode only: the link is printed in the backend terminal rather than emailed, so it only helps while you run the app yourself.
4. Login throttling is in memory and resets on restart.
5. A saved link's key lives next to the database unless `APP_ENCRYPTION_KEY` is set (see above).
6. A calendar link that the calendar service refuses (revoked or expired) shows a generic message; the saved copy isn't removed automatically (use "Forget this link").
7. The week picker moves within the 6 weeks read from this week; going further needs a new read (a pasted link that wasn't remembered must be pasted again, and uploaded files re-chosen).
8. The description, answers and plan are not saved between visits (page memory only).
9. The diet check can't judge free-text notes well (for example it will treat "I love peanut butter" as a peanut allergy) and can't verify hidden ingredients in store-bought items; the recipe lists every ingredient but the user must still read labels.
10. Workout suitability for an injury isn't verified by code.
11. **Class schedules that run on scripts or booking widgets can't be read** (for example Breathing Room Yoga's page); only studios with a plain-text timetable work. PDF timetables aren't read yet (it would need a PDF-reading package). Class times come from the studio's page on the day it was read and can change or be cancelled; the app never books or checks availability.
12. **Evidence limits.** The quotes come from public health pages read on Oct 16, 2026 and are general information, not advice for any one person; they can go out of date, so re-run the verification script now and then. The list covers movement, sleep, stress, connection and a few nutrition topics; some items (for example many meals, journaling) have no applicable claim, and then the app says nothing about benefits. CDC and Mayo Clinic pages were not used because they refuse automated downloads and could not be verified.
13. The check that a start time "appears in the page" is a text match, so a time that appears for another reason on the same page could pass; the studio and class names aren't matched against the page.
14. Removing and approving items happens in the page; the server only sees the final approved list at export time.
15. **Reservation availability is usually not readable.** Restaurants' booking widgets are drawn by scripts, so most results are suggestions with a link, not confirmed tables. Booking is always done by the user.
16. **Movie showtimes and streaming availability are usually not readable.** Theater sites draw showtimes with scripts and streaming guides rarely state a service in plain text, so most movie suggestions are "playing near you" or "check where to watch" with a link; availability can change.
17. Re-importing the same file twice creates duplicate events (each export gets new event ids).
